# libscpi.so

Асинхронный клиент SCPI для Linux. Использует C++17, Qt 6 Core и Network и прямое TCP-соединение через `QTcpSocket`. Один экземпляр `scpi::ScpiClient` обслуживает один прибор по заданному IPv4- или IPv6-адресу. Порт по умолчанию — 5025. [Схема взаимодействия и состояния](docs/architecture.md)

## Сборка и запуск

Понадобятся компилятор C++17, CMake 3.16+ и Qt 6.2+. Для сборки тестов нужен Qt Test. В Debian и Ubuntu с Qt 6 в репозитории зависимости можно установить так.

```sh
sudo apt install build-essential cmake qt6-base-dev
```

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
(cd build && ctest --output-on-failure)
```

`scpi_example` открывает соединение, читает `*IDN?`, выводит ответ и закрывает соединение. Для сборки только библиотеки добавьте `-DBUILD_TESTING=OFF -DSCPI_BUILD_EXAMPLE=OFF -DSCPI_BUILD_EMULATOR=OFF`.

```sh
cmake --install build --prefix "$PWD/install"
```

В приложении подключите `<scpi/scpiclient.h>` и свяжите цель с установленной библиотекой.

```cmake
find_package(Scpi CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE Scpi::scpi)
```

Передайте путь к префиксу в `-DCMAKE_PREFIX_PATH=/path/to/install`. Ту же цель можно использовать с `add_subdirectory`. Она автоматически подключает Qt Core и Network.

Готовая сборка 1.1.0 для Linux x86-64 содержит библиотеку, заголовки, пакет CMake и имитатор `bin/scpi_emulator`. Она собрана на Debian 13 с Qt 6.8.2. Распакуйте архив и укажите папку `libscpi-linux-x86_64` в `CMAKE_PREFIX_PATH`. [Скачать архив](dist/libscpi-linux-x86_64.tar.gz)

## Операции и состояния

Создавайте клиент и вызывайте его методы в потоке, где работает его цикл событий Qt. Приём, передача и подключение идут через события Qt. Сигналы доставляются через этот цикл, поэтому возвращённый идентификатор уже доступен к моменту обработки результата.

| Вызов | Результат |
|---|---|
| `setEndpoint(QHostAddress, port)` | Задаёт адрес и порт, когда рабочий сеанс закрыт и клиент свободен. При смене адреса или порта доступность сбрасывается в `Unknown`. |
| `open()` | Открывает рабочий сеанс. Повторный вызов во время подключения получает свой результат того же подключения. |
| `close()` | Закрывает рабочий сеанс и завершает его незаконченные операции с `Cancelled`. Для уже закрытого сеанса вызов успешно завершается. |
| `send(command, false)` | Завершается после записи всех байтов в локальный TCP-сокет. Вызов `send(command)` выбирает этот режим. |
| `send(command, true)` | Отправляет команду и отдельную строку `*OPC?` в одной операции FIFO. Завершается при полном ответе `1` или `+1`. |
| `query(command, format[, count])` | Всегда ждёт ответ и возвращает всю полезную нагрузку как один `QByteArray`. По умолчанию ожидается одно текстовое сообщение. |
| `checkAvailability()` | Завершается сигналом `availabilityCheckFinished(id, available, error, detail)` при каждом вызове, даже при выключенном мониторинге. |

`open`, `close`, `send`, `sendConfirmed` и `query` выдают по одному сигналу `operationFinished(id, response)` или `operationFailed(id, error, detail)`. Успешные `open`, `close`, `send` и `sendConfirmed` возвращают в сигнале пустой массив. Существующий вызов `sendConfirmed(command)` соответствует `send(command, true)`. При успешной разовой проверке `error` равен `Error::None`. Объект клиента должен жить до получения результата.

Команда передаётся одной строкой. Можно передать её с завершающим LF или CRLF. Клиент отправит один LF. При подключении команды можно добавлять в очередь сразу после `open()`. При закрытом сеансе обычные команды завершаются с `NotConnected`. Запросы очереди выполняются по одному.

`sessionState()` возвращает `Closed`, `Connecting`, `Connected` или `Reconnecting`. `availability()` возвращает `Unknown`, `Available` или `Unavailable` по итогам последней начавшейся проверки. Отмена проверки и ошибки до её начала сохраняют прежнее состояние доступности. `sessionStateChanged` и `availabilityChanged` передают значение на момент перехода и срабатывают один раз на каждый переход.

## Формат и предел ответа

| `ScpiClient::ResponseFormat` | Ожидаемый ответ |
|---|---|
| `Text` (по умолчанию) | Строка до LF. Для CRLF оба символа удаляются. |
| `IeeeBlockLf` | Блок IEEE 488.2 и LF после данных. |
| `IeeeBlockCrlf` | Блок IEEE 488.2 и CRLF после данных. |
| `IeeeBlockNoTerminator` | Блок IEEE 488.2, который заканчивается последним байтом данных. |

Каждый двоичный запрос указывает формат с нужным терминатором явно. Например, `client.query("TRAC:DATA?", ScpiClient::ResponseFormat::IeeeBlockLf)`. Блок имеет вид `#<N><length><data>`. В результат входят ровно `length` байтов данных, включая любые NUL и LF внутри блока. Блок `#0` приводит к `UnsupportedFormat`.

При фрагментации TCP одного сообщения обычный `query(command, format)` собирает его целиком. Если прибор отправляет несколько отдельных строк или двоичных блоков, передайте их ожидаемое количество в `query(command, format, count)`. Все сообщения одной операции имеют указанный формат. Текстовые строки соединяются через LF, полезная нагрузка двоичных блоков складывается подряд. Итоговый сигнал приходит один раз после последнего ожидаемого сообщения.

`setMaximumResponseSize(bytes)` ограничивает размер итогового массива. По умолчанию это 16 МиБ. В предел входят LF между строками, а заголовки и терминаторы кадров удаляются. Полный, но неожиданный ответ на `*OPC?` возвращает `UnexpectedResponse`. Следующая операция может начаться после такого ответа, поскольку его граница уже прочитана.

`setTimeouts({connectMs, responseMs, availabilityMs})` принимает положительные значения в миллисекундах. По умолчанию действуют 3000, 3000 и 1000 мс соответственно.

- Тайм-аут подключения ограничивает установление любого TCP-соединения.
- Тайм-аут ответа задаёт общий срок с начала обычной операции. Для `query` и `send(command, true)` он включает запись и чтение всех ожидаемых сообщений. Для `send(command, false)` он ограничивает запись.
- Тайм-аут проверки доступности включает временное подключение, если оно нужно, а также запись и чтение запроса. Параллельно действует лимит подключения.
- Отсчёт для операций очереди начинается, когда операция взята в работу. Текущая операция сохраняет лимиты, установленные на момент её запуска.

## Автоматическое восстановление

При тайм-ауте операции, повреждённом ответе или обрыве драйвер закрывает старый TCP-сокет и переводит рабочий сеанс в `Reconnecting`. Активная операция получает исходный код ошибки. Ожидающие операции старого сеанса получают `SessionLost`. Драйвер повторяет TCP-подключение. Отправку команды после ошибки решает приложение.

Настройки задаются через `setRecoveryPolicy({enabled, maxAttempts, initialDelayMs, maxDelayMs})`. По умолчанию доступны пять попыток с задержками 250, 500, 1000, 2000 и 4000 мс. У каждого подключения собственный тайм-аут. Новая настройка действует со следующей серии повторов. Вызов `close()` отменяет текущую серию. Чтобы отключить повторы, передайте `{false}`.

Новые операции, поставленные в очередь во время восстановления, ждут успешного подключения. При исчерпании попыток сеанс становится `Closed`, а очередь получает `SessionLost`. Если сбой произошёл при первом `open()`, его результат приходит после подключения или исчерпания всей серии.

## Проверка доступности

`setAvailabilityCommand(command)` меняет стандартный `*IDN?` на другой запрос с текстовым ответом. Прибор считается доступным, если получена полная строка с хотя бы одним непробельным байтом. При открытом рабочем сеансе разовые проверки идут через общую очередь. При закрытом сеансе каждая проверка открывает и закрывает временное соединение с тем же адресом и портом.

`startMonitoring(intervalMs)` запускает периодические проверки. Первый запуск происходит после заданного интервала. Такт пропускается во время подключения, восстановления, выполнения операции и при занятой очереди. При закрытом рабочем сеансе свободный клиент проверяет прибор временным соединением. `stopMonitoring()` отключает новые запуски и даёт завершиться уже отправленной проверке. Периодическая проверка сигнализирует через `availabilityChanged` только при переходе состояния. Разовые проверки работают независимо от таймера.

## Проверка применённого значения

Ответ на `*OPC?` подтверждает завершение операций прибора. Для проверки самого значения прочитайте параметр отдельным запросом. В примере ниже `client` уже подключён к источнику питания, который поддерживает `SOUR:VOLT` и `SOUR:VOLT?`. Объекты `client`, `app` и переменные идентификаторов живут до завершения обоих запросов. Для фрагмента нужны `<QDebug>` и `<cmath>`.

```cpp
using scpi::ScpiClient;

ScpiClient::OperationId setId = 0;
ScpiClient::OperationId readbackId = 0;
constexpr double requestedVolts = 5.0;
constexpr double toleranceVolts = 1e-6;

QObject::connect(&client, &ScpiClient::operationFinished, &app,
                 [&](quint64 id, const QByteArray &response) {
    if (id == setId) {
        readbackId = client.query("SOUR:VOLT?");
    } else if (id == readbackId) {
        bool ok = false;
        const double volts = response.toDouble(&ok);
        if (ok && std::abs(volts - requestedVolts) <= toleranceVolts)
            qInfo() << "Подтверждено значение" << volts << "В";
        else
            qWarning() << "Ожидалось 5 В, получено" << response;
    }
});
QObject::connect(&client, &ScpiClient::operationFailed, &app,
                 [&](quint64 id, ScpiClient::Error error, const QString &detail) {
    if (id == setId || id == readbackId)
        qWarning() << id << error << detail;
});

setId = client.send("SOUR:VOLT 5", true);
```

## Имитатор прибора

В одном терминале запустите имитатор. По умолчанию он слушает `127.0.0.1:5025`. Аргументы ниже делят ответ на записи по 8192 байта и добавляют паузу между ними.

```sh
./build/scpi_emulator --port 5025 --chunk-bytes 8192 --chunk-delay-ms 1 --binary-terminator crlf
```

В другом терминале запустите пример драйвера.

```sh
./build/scpi_example 127.0.0.1 5025
```

| Команда | Поведение прибора |
|---|---|
| `*IDN?` | Строка идентификации прибора. |
| `SOUR:VOLT 12.5`, `SOUR:VOLT?` | Установка и чтение напряжения. Уставка сохраняется между подключениями. |
| `*OPC?` | Ответ `+1` после обработки предыдущих команд. |
| `SIM:TEXT? 70000,3` | Три текстовые строки по 70 000 байтов. |
| `TRAC:DATA? 524288,3` | Три блока IEEE 488.2 по 512 КиБ с заданным терминатором. |
| `SIM:DELAY? 5000` | Текстовый ответ с задержкой 5000 мс. |
| `SIM:DROP?` | Закрывает соединение. Следующее подключение принимается как обычно. |
| `SIM:BAD?` | Возвращает блок `#0` для проверки обработки ошибки формата. |

Большие ответы в примере можно получить следующими запросами. Для блока указан CRLF в соответствии с запуском имитатора выше.

```cpp
using Format = scpi::ScpiClient::ResponseFormat;
const auto textId = client.query("SIM:TEXT? 70000,3", Format::Text, 3);
const auto traceId = client.query("TRAC:DATA? 524288,3", Format::IeeeBlockCrlf, 3);
```

## Что проверяют тесты

`scpi_parser_tests` подаёт ответы с разбиением по каждой границе байтов и проверяет форматы, предел длины и лишние байты. `scpi_client_tests` работает с локальным `QTcpServer`. Он проверяет FIFO, фрагментированные ответы, `*OPC?`, разрыв соединения, тайм-аут с поздним ответом, отмену и отсутствие повторных сигналов мониторинга при одинаковом результате.

`scpi_recovery_tests` проверяет подключение после сбоя, завершение серии повторов и отмену через `close()`. `scpi_emulator_tests` проверяет драйвер через имитатор, включая чтение уставки, восстановление после разрыва и сборку ответа из трёх двоичных блоков общим размером 1,5 МиБ.
